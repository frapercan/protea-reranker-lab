# What the champion's 64 features actually do

Receipt: `gain_report.json`, regenerated by `measure_gain.py` (reads the three
sealed boosters, no database, no network). Frame v227 to v230, the sealed
`f_micro_w` 0.4063 champion.

## The shape of it

**Sixteen of the 64 features carry 95% of the total split gain.** The top five
alone carry 78.5%.

| feature | share of aggregate gain |
|---|---|
| `go_term_frequency` | 25.47% |
| `anc2vec_query_known_maxcos` | 19.36% |
| `lineage_is_ancestor_of_known` | 12.69% |
| `k_position` | 11.71% |
| `anc2vec_neighbor_cos` | 9.30% |
| `vote_count` | 3.42% |
| `anc2vec_neighbor_maxcos` | 3.39% |
| `identity_nw` | 2.17% |

## Lineage is a per-cell story, and that is the point

| cell | lineage share of that cell's gain |
|---|---|
| no-knowledge | **0.00%** |
| limited-knowledge | 0.30% |
| previously-known | **25.58%** |

`lineage_is_ancestor_of_known` is the second most important feature of 64 in the
previously-known cell (20.55% of it) and the third overall. In the no-knowledge
cell all four lineage columns score exactly zero, and they must: the producer
writes a well-defined `0.0` when the protein has no known terms, and with no
known terms there is nothing to be an ancestor of.

An aggregate table would have hidden this. A feature that is dead in one regime
and decisive in another is not a marginal feature, it is a regime detector. This
is why the nine-cell grid exists.

## Twenty-eight features have gain exactly zero

LightGBM never split on any of them, in any of the three cells:

- **The sixteen `emb_pca_query_*`.** A PCA projection of the query embedding.
  **CORRECTED 2026-07-16, and the correction reverses this entry.** The earlier
  reading here said they were "populated, and worth nothing to the booster",
  and concluded the retrieval encoder already carries whatever they encode.
  That is wrong. These columns were **all-NaN**, never populated at all. They
  are gated by `use_embedding_pca`, which defaults to `False` at every single
  declaration site (`export_research_dataset.py:73`,
  `export_minijobs/_export_features_batch.py:64`,
  `export_minijobs/_export_knn_batch.py:57`,
  `export_minijobs/export_coordinator.py:74`, `training_dump/_payload.py:113`,
  `api/routers/datasets.py:159`). With the flag off, `pca_state` is None and
  `_KnnTransferRunner._compute_pca_proj` emits NaN by design; the code's own
  docstring says so ("NaN when ``pca_state`` is None"). LightGBM reports zero
  gain for an all-NaN column because it **cannot split on it**, not because the
  signal is redundant. The family is therefore **unmeasured, not refuted**, and
  the `gain_report.json` this receipt is built from carries no populated-ness
  statistic that could have distinguished the two.

  One design note explains why nobody turned it on: `use_embedding_pca` is
  documented as a *retrieval* knob (project embeddings through the cached PCA
  **before KNN**: smaller index, slight Fmax loss), yet the same boolean also
  switches these 16 feature columns. Producing the features currently costs
  retrieval quality, because the two concerns share one flag.
- **The eight `interpro_*` plus `interpro_present`.** Zero for a different
  reason, and the earlier reading of that reason (2026-07-10) was wrong.
  These features do NOT read the `interpro_annotation` / `interpro_go_mapping`
  database tables. They read a TSV named by the `PROTEA_INTERPRO_GO_PRED_PATH`
  environment variable (`protea/core/_interpro_features.py`), and its own
  docstring is explicit: when the variable is unset or the file is absent at
  load time, the join is empty and every record keeps the default. Verified on
  2026-07-11: the variable is not set in `~/.secrets/protea.env`, no such TSV
  exists, so the sealed dataset was exported with the InterPro source
  unconfigured. This is a configuration gap, not a broken producer and not
  empty DB tables (those tables feed a different operation,
  `predict_go_terms_from_interpro`). InterPro still contributes +0.0179
  `f_micro_w` through a separate noisy-OR graft that reads `interpro2go.txt`
  and `protein2ipr.json` directly, which is unaffected. To make these features
  carry signal, materialise the InterPro GO-prediction TSV, point
  `PROTEA_INTERPRO_GO_PRED_PATH` at it, and re-export.
- `anc2vec_has_emb` and `knn_present`: constant in practice.

## What follows, and what does not

**Retiring neither family is defensible on this evidence.** The earlier version
of this section said retiring `emb_pca_query_*` was defensible "because the
signal is populated and contributes nothing". Both halves of that were false:
the signal was not populated, and a family that never reached the model cannot
be said to contribute nothing. There is no evidence against it, only an absence
of evidence. Retiring `interpro_*` is not defensible either, for the separate
reason that it would bury a configuration gap under a statistic, and the
graft's +0.0179 is what secures seven of the nine cells.

Both families are also still **fully declared** in the contracts schema
(`feature_schema.py`), 27 columns across the two, with no deprecation marker,
no dormancy marker, and no producer-liveness annotation. The schema's only
vocabulary is "declared": it cannot express "declared, but no producer is wired
in this deployment". So the contract asserts 27 features exist while the export
ships 11 of them as constant zeros and 16 as constant NaN, and nothing records
the discrepancy.

A gain of zero is a fact about **this booster on this frame**, not a verdict on
the signal. Regenerate this receipt after any retrain before citing it.

That rule is the one this receipt broke. It was stated here from the first
draft, two paragraphs below a claim that read a zero as a verdict on the
signal. Writing the rule down is not the same as applying it: the check that
would have caught this is cheap and specific, which is **has this column any
non-null value at all**, and it was never run because the number looked
explicable. Ask what a zero is made of before deciding what it means.
